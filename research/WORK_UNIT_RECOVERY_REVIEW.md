## Pre-execution code disposition

**Approved for the three registered lead-only subprocesses.** The supervisor exclusively reserves each phase before `Popen`, pins source inputs, waits for an observed exit code, matches the child's PID/phase/completed output, hashes the output into a parent-written receipt, verifies that the child's lead remains active, then terminates that token and saves a post-exit audit. Only a completed earlier ledger row permits the next phase. Timeout is unknown and no replacement is launched; nonzero/malformed output stops the sequence. A prior phase is not allowed to certify its own termination.

The child validates the prior parent receipt, exact output hash and PID, and the post-exit terminated-token audit before acquiring the next lead. Phase 1 reserves one dummy unit and writes one exclusive marker while leaving the work unresolved to simulate lost acknowledgment. Phase 2 checks the running attempt and reserved work, demands the *specific* same-ID and new-ID unresolved rejection reasons before callback, verifies marker bytes before reconciliation, then executes and settles one second dummy callback. Phase 3 demands terminal replay without callbacks and a specific cap rejection, verifies that the evidence directory contains exactly two deterministic markers, and finishes the one attempt with a hashed dummy-software artifact. The supervisor checks distinct observed PIDs. Source/marker/phase outputs are exclusive, and the cap is two cumulative units.

Review required repairs before approval: generic catches of any `Blocked` could have falsely counted stale-lead or wrong-attempt errors as the intended gate; those now inspect exact reasons and persisted pre-probe state. The supervisor now verifies active lead state before parent retirement, and the child explicitly adds repository root to its import path. The PID and exact marker-set checks are present. The final `Result` is labeled inconclusive dummy recovery, not a biological result.

## Observed execution and final disposition

**The three-process recovery claim is not accepted. Stop after phase 1.** The supervisor's one reserved invocation launched the configured `.venv/Scripts/python.exe` and observed its `Popen` PID **12896** exit with code 0 at 16:38:37.489082 UTC. The saved `phase-1.json` reports a different PID, **6280**, so the registered process-identity check failed. The supervisor marked the invocation `failed_supervision` in [the execution ledger](work_unit_recovery_execution.json); there is no accepted `exit-1.json` receipt or post-exit audit, and phases 2 and 3 were not launched. The child output and marker show that one dummy callback wrote its deterministic evidence, while its audit records one `reserved` work unit, one running attempt and active lead token 1. Those records do not prove that the process observed by `wait` was the process running the Python body or that the latter exited when the former did. The apparent Windows venv redirector is an unverified explanation, not an accepted ancestry proof.

The lead's later [process lookup](work_unit_recovery_001/process_lookup_cmdlet.json) at 16:40:05 UTC returned an explicit `NoProcessFoundForGivenId` for both 12896 and 6280. This establishes that neither ID was present at that later observation. It does **not** recover the child Python process's exit code or establish wrapper/child ancestry and exit ordering. Earlier CIM access denial and .NET ConstrainedLanguage errors yielded invalid empty inventories and must not be counted as absence evidence.

This is a **supervision/identity failure**, not evidence that the work-unit controller lost state or exceeded its cap. Do not terminate or reconcile the token from a mismatched receipt, relaunch the same phase, reset the reservation ledger, or infer completion from elapsed time. A separately registered, zero-work process-identity preflight may test a direct base interpreter by comparing its parent-observed `Popen` PID with a child-reported PID and exit. Any subsequent recovery design must explicitly preserve this consumed phase invocation, dummy callback and unresolved work accounting; it cannot silently create a replacement campaign or budget. The current attempt demonstrates neither forced-crash/reboot recovery, live-agent enforcement nor exactly-once external effects.
