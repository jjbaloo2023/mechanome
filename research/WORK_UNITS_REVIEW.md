# Independent review: offline cumulative work-unit guard

Task `offline-work-units-review-001`, 29 September 2026. I read the registered [design](work_units_design.json), the prior contracts/controller/tests, the implementation diff and the new dummy-work tests. I did not import or execute the implementation, tests, callbacks, trackers, fits or BVPs.

## Code and contract assessment

The extension adds normalized immutable per-kind limits to both charter and task, and an SQLite `work_units` record keyed by task and stable call ID. `reserve_work` fences the lead and checks both lifetime caps under `BEGIN IMMEDIATE` before permitting a callback. Every reservation counts, including terminal failed/cancelled work; this deliberate no-refund rule survives retries and restart. A terminal duplicate is explicitly non-executing, changed kind/units conflict, and reserved/unknown work blocks a new call ID, attempt finish and retry until evidence-bearing reconciliation. New work-state transitions are fenced; legacy attempt `finish` and `uncertain` are not newly fenced. Export includes individual work rows and totals. This is an offline primitive, not live agent/provider integration or a guarantee of exactly-once external effects.

I required and inspected two material repairs before approval. The first draft checked unresolved status only for a duplicate call ID; another ID could bypass it. The final `reserve_work` rejects *any* new call ID while the task has reserved/unknown work. The initial tests also failed to actually redeliver old JSON and set campaign and task caps equal while expecting a task-cap error. The revised tests use default-empty old bodies, reopen and redeliver without rewriting them, and separate the campaign/task cap values. Kind spelling is canonicalized so whitespace variants cannot consume separate caps.

The wrapper intentionally leaves a returned or raised callback's reservation unresolved until the caller provides terminal evidence. This is conservative but imposes a real caller duty: an un-reconciled successful call blocks task finish and any replacement. The final tests separately check a returned callback, a raised callback left reserved, a sequential reopen/stale-lead path, and two simultaneous fresh SQLite connections racing for one campaign unit. The race asserts exactly one reservation, and the barrier and joins are time-bounded. These are dummy-work checks; they do not simulate a full host reboot or external side effects.

**Disposition: accept the bounded offline extension.** The lead's single targeted pytest invocation ran the 11 existing and six new tests, **17 passed**, exit 0; [log](work_units_pytest_01.log) and [execution ledger](work_units_test_runs.json) record exact tested source hashes, one invocation and zero scientific calls. The current source/test hashes match that ledger. API-level terminal work records cannot be reconciled again, and immutable event entries preserve transitions in the export. Existing money, review-reserve, attempt and artifact semantics remain covered by the old tests. This does **not** claim the new controller would have prevented the earlier live synthetic-dimming overrun without wiring live execution through it; preserve that historical protocol failure.
